Module: R5 Stop/Cancel server endpoint

- Implemented a server-side cancellation workflow for Discovery jobs.
- Added API endpoint: POST /api/dev/discovery/jobs/[jobId]/cancel to mark a job as cancelled (status = "cancelled").
- Extended DiscoveryJobStatus with a new value: "cancelled" so cancellation is persisted in KV/file stores.
- Workers bail early on cancelled jobs to avoid unnecessary work (executeJob now checks for cancelled status before acquiring the process-wide harvest lock).
- UI wiring: Stop button already triggers server-side cancellation via the new endpoint; cancelled jobs propagate to UI via existing GET /api/dev/discovery/jobs/:id route.
- Updated typings in provider-health component to recognize the new job status value.
- Tests: existing unit tests (tests/domain/discovery-harvest.test.ts) cover executeJob flow and can exercise cancellation with a cancelled job in a memory store if extended test is added; the new code is designed to be testable with a simple MemoryStore path.

- Files touched:
- src/discovery/jobs.ts (extend DiscoveryJobStatus)
- src/discovery/harvest.ts (early-cancel check via getJob, log attempt)
- src/app/dev/mission-control/_components/provider-health.tsx (DiscoveryJob type union extended to include "cancelled")
- src/app/api/dev/discovery/jobs/[jobId]/cancel/route.ts (new cancel endpoint)
- Minor: no changes to public interfaces beyond adding the new status variant; existing routes keep working.

- How to validate locally:
- Run tests: npm test (Vitest) or pnpm test as configured. Ensure test suite passes with new status.
- Manually trigger: POST /api/dev/discovery/run to enqueue a job; then POST /api/dev/discovery/jobs/{jobId}/cancel to cancel; verify GET /api/dev/discovery/jobs/{jobId} shows status "cancelled".
- Optional: extend tests to assert idempotent cancellation (repeating cancel should be a no-op).
