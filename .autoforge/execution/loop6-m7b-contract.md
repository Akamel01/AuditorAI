## Fixes

**F1 (M1) — licence dimension.** The coverage-candidate rule has no licence dimension, so a
Crown-copyright document counts as coverage. Do not silently drop such candidates (the corpus's
`canada/` shelf is RESTRICTED pending owner sign-off, `docs/RSA-Documents/LICENSE-REGISTER.md:12`,
so dropping them would zero every cell). Instead: keep the count, and disclose it — for every
counted candidate show its licence state, and state that a candidate whose licence is not CLEAR is
not usable for train/test until the owner signs off. The corpus licence state is read from
`docs/RSA-Documents/LICENSE-REGISTER.md` (directory -> verdict); a candidate whose directory is not
listed there is reported as `unknown`.

**F2 (M4 + M2) — label provenance and the corpus root.** 134 of the 304 inventory rows carry
`label_confidence: needs_review` and their labels are rule-derived, not audited; the report must
say so and show the per-cell breakdown of label confidence (`anchor` / `rule` / `needs_review`).
Also split the row sets by corpus membership: rows whose path is under `docs/RSA-Documents/` (the
corpus root) versus rows outside it (`docs/references/`, `tests/fixtures/`, `tmp/harvest/` — 102
rows). One of the counted candidates is a **test fixture**
(`tests/fixtures/samples/CA/ab-neahd-planning-stage-rsa-2009.pdf`, sha `0af7ea58…`), which is
byte-identical to the ingested corpus copy — say that explicitly instead of letting "On disk 0 |
Fetched 1" hide it.

**F3 (M3) — manifest-only rows are not all samples.** The builder hard-codes class
`rsa-sample` for manifest-only rows, so a T1 guide (`t02-04b.pdf`, `doc_type: guide`) counts as a
true sample while its sibling counts as methodology. Classify a manifest row from the data the
manifest actually carries: tier T3/T4 -> sample, T1 -> methodology/other, T0 -> unusable. Keep the
inventory classification rules untouched.

**F4 (M5) — where a label came from.** A fetched row's tier/stage may come from the text signals
or from the source manifest's fallback (`stage_hint`, `doc_type_hint: complete-RSA` -> T3); the
manifest does not record which path was used. Disclose the rule and count the fetched rows whose
stage equals the source `stage_hint` (the fallback path) so the reader can see how much is
hint-derived rather than read out of the document.

**F5 (M6) — the "never re-downloaded" claim is false.** The hash gate is applied AFTER the bytes
arrive (`scripts/harvest-track-a.ts:547-567`), so a document whose hash the corpus already holds
IS downloaded and then discarded — the committed outcome blocks record 10 such downloads. Correct
every claim: in `.autoforge/execution/M6b.md` and in the `ab-publications-listing` outcome block
(and any other outcome block that claims "never re-downloaded"), say **never re-ingested** and give
the number of documents that were downloaded and discarded.

**F6 (M7) — the duplicates register is now partial.** Because the hash skip happens before staging,
`docs/RSA-Documents/track-a-duplicates.json` can only hold the rows staged before that rule (2
rows). Say so wherever the register is presented (the report's fetched-only section), so nobody
reads it as "only 2 duplicates ever existed".

**F7 (M8) — the two coverage artefacts must not contradict each other.**
`docs/RSA-Documents/track-a-coverage.md:13` says `canada:DETAILED_DESIGN` fetched 0 while
`docs/RSA-Documents/track-a-harvest-report.md` says 1. They measure different things (fetched-only
vs inventory-derived). State that difference in the report, name both files, and fix the stale
lines in `.autoforge/execution/M6b.md:51-53` so the brief matches the committed artefacts.
