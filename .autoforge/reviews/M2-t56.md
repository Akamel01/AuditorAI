## Blocking

**B1 — the runbook's manual restore applies the migrations to the wrong database.**
`docs/runbooks/restore.md:46-51` (verbatim):
```
export RESTORE_DATABASE_URL='<scratch-url>'
pg_restore --schema=public --no-owner --no-privileges --exit-on-error -d "$RESTORE_DATABASE_URL" restore-work/dump.pgcustom
psql -v ON_ERROR_STOP=1 -f supabase/migrations/0003_roles.sql
psql -v ON_ERROR_STOP=1 -f supabase/migrations/0004_seats_invites.sql
psql -v ON_ERROR_STOP=1 -f supabase/migrations/0005_audit_trail.sql
psql -v ON_ERROR_STOP=1 -c 'ANALYZE;'
```
`psql` does not read `RESTORE_DATABASE_URL`. With no `-d "$RESTORE_DATABASE_URL"` (or positional URL), lines 48-51 connect to `$PGDATABASE`/the OS user's default database. Role creation, grants, column grants, policies and `ANALYZE` therefore hit the wrong DB or fail; only `pg_restore` (line 47) targets the scratch target. Fix: pass the URL to each `psql` call, and note the host `pg_restore`/`psql` must be PG17 (the dump is a `postgres:17` custom archive) or use the Docker wrapper from `restore.sh:105-111`.

A real restore whose first two workspaces have no projects fails the probe (false fail); plan-mandated, but the runbook should tell the operator to pick/seed a pair with projects.

- `pg_restore --schema=public` is correct: PG17 `_tocEntryRequired` drops NULL-namespace entries (`pg_backup_archiver.c:3094-3100`), while `pg_dump --schema=public` emits `CREATE SCHEMA public` (`selectDumpableNamespace` leaves `create=true`; `dumpNamespace` has no `.namespace`). No object loss here: no sequences (only `gen_random_uuid()`), no public extensions (`selectDumpableExtension`: no extensions with `--schema`), and `SEQUENCE OWNED BY` carries a namespace.
- Re-applying 0003→0005 on a `--no-privileges` dump is safe: 0003 role/membership `if not exists` + grants; 0004 `add column if not exists`/`drop policy if exists` + column grants; 0005 `create table if not exists` + policy drops/creates + re-grants. `rls_catalog`/`rls_role`/probe all use `ON_ERROR_STOP=1`, so a raised `DO` exits the step.
- Evidence claim `.autoforge/execution/M2.md:13` ("TENANT_POSTGRES_URL grep -> no matches") is false: `scripts/backup/backup.sh:51` and `docs/runbooks/restore.md:62` contain the string. `restore.sh` never reads it; the runbook mention is the required re-point text. Flag for the evidence record.

- Security: no real endpoint/key/password; endpoint grep empty; no `/home/oc`; fail-closed exits 1 before Docker. `RESTORE_DATABASE_URL` is in the container env/argv (not logs), same caveat as the backup critique C3.
