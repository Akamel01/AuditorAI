## Findings — non-blocking (ranked)

**N1 — The M6b round covered one of nine sources, and the manifest's `m6_*` counters mix rounds.**
`/tmp/m6b-fetch.log:1-15` contains a single `[ab-publications-listing]` section, so the round ran
with a `--source` filter even though the contract command was `fetch --live --max=<n>`
(`loop6-m6-split.md:50`). The other seven `m6_*` outcome blocks
(`docs/RSA-Documents/track-a-sources.json:57-60`, `:87-90`, `:153-157`, `:189-191`, `:219-223`,
`:250-254`, `:283-286`) were committed in `913b4ba` by an earlier, interrupted round. M6b.md:26-28
tables only the new source and never says the other counters predate this round, so a reader of the
manifest can wrongly attribute them to M6b.
*Fix:* in `.autoforge/execution/M6b.md` and in the PR body, state that only
`ab-publications-listing` was attempted in this round and that the other `m6_*` counters are
inherited from the earlier round; or add a `"round": "m6b"` marker to the new outcome block.

**N2 — The per-skip evidence is not in git.** The only durable trace of the round is the aggregate
`outcome` block (`docs/RSA-Documents/track-a-sources.json:119-127`); the 12 candidate URLs and their
skip reasons live only in `/tmp/m6b-fetch.log`, which is container-local and will not survive. AC1
of the ticket asks for a coverage table in the PR body, whose numbers would then rest on an
uncommitted file.
*Fix:* commit `/tmp/m6b-fetch.log` as a text artefact (e.g. `docs/RSA-Documents/track-a-fetch-log-m6b.txt`)
or inline the 12 candidate/skip lines into the `outcome` block — both are git-safe text.

**N3 — A PDF text-extraction warning is folded into the "not RSA" skip reason (false-negative risk).**
`/tmp/m6b-fetch.log:10` records `UnknownErrorException: Ensure that the standardFontDataUrl API
parameter is provided.` immediately before the skip of `neahdappendixeappendices.pdf` (`:11`).
`scripts/harvest-track-a.ts:568-585` extracts text and, when extraction warns but does not throw,
the document is classified and dropped as "not RSA" with no separate signal. One of the nine
"not RSA" verdicts may therefore be a text-extraction artefact rather than a content judgement, and
the same weakness would silently shrink every future round.
*Fix:* pass `standardFontDataUrl` to `extractText`, and record an extraction warning as its own skip
reason (e.g. `text-extraction-warning`) so a suspicious classification is visible in the round record.

**N4 — `sourceEntryProblem` still crashes on a `null` entry and does not validate the enums.**
`scripts/harvest-track-a.ts:137-148` dereferences `source.id` immediately; a `null` element in
`manifest.sources` (hand-edited JSON) throws `TypeError: Cannot read properties of null` at
`:138` — exactly the crash class the guard was added to prevent. The guard also accepts an unknown
`strategy` string (it falls through to the atom-feed branch at `:330-350`, silently fetching a feed)
and an out-of-enum licence verdict (which `splitFor` would map to `restricted`, `:356-359`).
*Fix:* `if (!source || typeof source !== "object") return "entry is not an object";` plus a check
that `strategy` is one of the four supported values and `licence_default.verdict` is
CLEAR/RESTRICTED/BLOCKED.

**N5 — `readIntakeManifest` turns a malformed manifest line into a crash of `intake`.**
`scripts/harvest-track-a.ts:644-650` maps `JSON.parse` over the manifest lines with no guard, and
`runIntake` now calls it (`:667`) where it previously did not read the manifest at all — so one bad
line in `canada-intake-manifest.jsonl` now aborts the intake before anything is written. The
tolerant pattern already exists in the same file for the inventory (` :186-195`).
*Fix:* wrap the per-line parse in try/catch and skip malformed rows, as `knownHashes` does.

**N6 — The split map's label is per province, but the manifest's split is per document.**
`scripts/harvest-track-a.ts:369-384` files a province under the most restrictive verdict seen for it
(`:376-380`). If a province ever holds a CLEAR row and a RESTRICTED row, the CLEAR document — whose
manifest row says `train`/`test` — is listed under a `restricted` province in
`track-a-split.json`, so the two artefacts disagree. The current corpus does not trigger this (AB
holds only CLEAR rows, BC only RESTRICTED ones, `canada-intake-manifest.jsonl:1-3`), and the
behaviour is conservative (no leakage into train/test), but it is a silent policy. Also,
`splitByProvince` recomputes the split from `licence_verdict` and ignores the recorded `split`
field, so a legacy row without `licence_verdict` would be relabelled `restricted`.
*Fix:* prefer the recorded `r.split` when `licence_verdict` is absent, and (optionally) emit a
per-document split next to the province label.

**N7 — `track-a-duplicates.json` is a per-run snapshot and can lose older rows.**
`scripts/harvest-track-a.ts:689-701` overwrites the file with only the duplicates found in that run,
so an intake run that finds two duplicates would drop the two rows committed today
(`docs/RSA-Documents/track-a-duplicates.json`). This is the same class of data loss H1 was about,
on a different file; the contract did ask for a "refresh" (`loop6-m6-split.md:21-26`), so it is
per-spec — but the operator-facing register loses history.
*Fix:* merge with the existing rows by `sha256` instead of overwriting, or document the
snapshot semantics in the file's `note`.

**N8 — Two fields on the new source entry are inert.** `max_candidates: 12`
(`docs/RSA-Documents/track-a-sources.json:117`) is honoured only in the `sitemap-keyword` branch
(`scripts/harvest-track-a.ts:279`); the `html-listing-pdf` branch (`:301-327`) has no candidate cap,
so candidate enumeration is bounded only by `max_listing_pages` (4 detail pages) and the number of
PDF links per page. Downloads are bounded by `max_downloads` (`:518`). `document_url_template`
(`:100`, declared at `:77`) is never read by any code path.
*Fix:* either apply `max_candidates` in the `html-listing-pdf` branch or drop the field from the
entry; drop `document_url_template` or wire it.

**N9 — The H3 note says "this run" inside a permanent artefact.**
`scripts/harvest-track-a.ts:790-791` and `docs/RSA-Documents/track-a-coverage.md:8`. The coverage
file is regenerated by `report`, which the operator is expected to run on their Mac; a regeneration
there would stamp "Binaries fetched by this run live in the box-runner container" while the binaries
are on the Mac.
*Fix:* phrase it run-independently ("Binaries fetched by container runs live in the box-runner
container … they are not in the operator's checkout") or stamp the host and date.

**N10 — Test hygiene.** `tests/discovery/harvest-track-a.test.ts:360` creates a `mkdtemp` scratch
root per test and never removes it (the container now holds ~10 leftover `/tmp/track-a-intake-*`
directories). The "agrees with `splitFor` on every province and verdict" test (`:322-329`) is close
to tautological (it asserts that a wrapper agrees with the function it wraps) — the load-bearing
tests are the byte-identity ones and the multi-province map (`:311-321`).
*Fix:* `rmSync(scratch, {recursive: true, force: true})` in an `afterEach`; keep the agreement test
but assert a couple of concrete values instead of the identity.

**N11 — Pre-existing selftest quirk (not an M6 regression).**
`scripts/harvest-track-a.ts:970-975` files every non-`train` province into the *test* set, so
`restricted`/`quarantine` documents are counted as test geography. Harmless today (the overlap
check is still meaningful), but the invariant is stated as "no document is in both train and test"
and should read `restricted`/`quarantine` as neither.
*Fix:* three-way classification in the selftest loop.

**N12 — Stale file:line citation in the worker's brief.** `.autoforge/execution/M6b.md:14` cites
`candidatesFor` at `scripts/harvest-track-a.ts:245-246`; after M6b inserted 18 lines at `:129`,
the `known-document-url` branch is at `:264`. The contract requires `file:line` for every asserted
fact, and this one now points at the `withHostBudget` call.
*Fix:* correct the citation to `:264`.

## Residual risks

- **Recall is unmeasured.** "0 fetched" rests on a text classifier over extracted PDF text, and
  the round itself logged an extraction warning (N3). M7 measures *precision*, so a systematically
  weak extractor would show up as a quietly small corpus rather than as a failure. A cheap
  mitigation is a per-round count of documents dropped for extraction reasons.
- **H3 is asserted, not exercised.** No binary was fetched in this round, so the container-vs-operator
  distinction is only a sentence in a markdown file; the first real binary must be checked against
  it.
- **Seven of nine source outcomes are inherited** from an earlier interrupted round (N1) and were
  not re-verified here.
- **The RC-3 test's precondition is data-dependent.** It assumes the committed `dedupe-index.json`
  still contains the three manifest hashes (verified today); if that index is ever regenerated
  without them, the staging rows would be ingested as fresh and the test's premise would silently
  change.
- **The full `npm test` was run with `tests/domain/vault-compile.test.ts` excluded**, because that
  test executes `node scripts/vault-import.mjs` with `cwd` = repo root and would rewrite
  `state/vault-notes.json` in a tree that has a live foreign lane (`AGENTS.md`, "Vault
  determinism"). Result at HEAD: 69 files, 707 passed, 2 skipped — the M6/M6b file is green.
  `npm run typecheck`, `npm run lint` and the CLI `selftest` were run in full and are clean.
- **Not verified (no network, per the constraints):** the live robots posture of
  `open.alberta.ca/publications`, the 10 s crawl delay and the 1 req/s/host budget during the
  round. The code honours them (`scripts/harvest-track-a.ts:238-252`, `:528-535`;
  `src/discovery/robots.ts`; `src/discovery/ratelimit.ts:33-52`), but the round's compliance rests
  on the worker's log.
- **Working-tree hygiene:** `.autoforge/state.json` and `state/production-harvest-proof.json` remain
  modified by the orchestrator and the background harvest-verify process respectively. Neither was
  staged or committed by M6a/M6b; the latter rewrites itself every few minutes and will dirty the
  tree again.
