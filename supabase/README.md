# AuditorAI tenant store — Supabase Postgres (ca-central-1)

This directory holds the paste-ready SQL for the ticket's tenant store: the
schema (10 tenant tables), the row-level-security policies, and the
non-bypass application role. Region: **ca-central-1** (pinned in the `0001`
header).

Nothing in the application imports these files. **No agent ever applies them.**
They are applied by the operator, by hand, to the live project.

## Files (apply in this order)

| File | What it does |
|---|---|
| `migrations/0001_tenant_schema.sql` | 9 tenant tables: `workspaces`, `workspace_members`, `workspace_credentials`, `projects`, `audits`, `audit_issues`, `attachments`, `artifacts`, `artifact_summaries` |
| `migrations/0002_rls_policies.sql` | `ENABLE` + `FORCE ROW LEVEL SECURITY` on all 9 tables, the three claim helpers, and every policy |
| `migrations/0003_roles.sql` | creates `auditorai_app` (NOSUPERUSER, NOBYPASSRLS, owns nothing) and grants it DML + `USAGE` + `EXECUTE` |
| `migrations/0004_seats_invites.sql` | ticket #54: `workspaces.seat_count` (default 1), membership state columns, three actor columns, two claim helpers, the four `workspace_members` policies and the column-level privilege hardening |
| `migrations/0005_audit_trail.sql` | ticket #55: adds the tenth tenant table `audit_trail_entries` (append-only, hash-chained firm history) with RLS enable+force, select/insert policies, revoked update/delete, and an append-only trigger |

`0002` and `0003` depend on `0001`; `0003` grants execute on functions created
by `0002`. Do not reorder, do not skip. The migrations are re-runnable:
`0002` drops each policy before recreating it, so a re-apply is safe.

## Operator procedure — the cutover, IN THIS ORDER

The tenant path is **explicit**: it runs only when `TENANT_STORE=postgres` is
set, and it reads `TENANT_POSTGRES_URL` (the pooled `auditorai_app`
connection string). `POSTGRES_URL` is NEVER read by the app.

```bash
# 0. prerequisites: the operator's shell has the connection string; it is never in the repo
export POSTGRES_URL_NON_POOLING='<operator-supplied direct connection string>'

# 1. apply in order (the Supabase SQL editor accepts the same three files pasted in this order)
psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 -f supabase/migrations/0001_tenant_schema.sql
psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 -f supabase/migrations/0002_rls_policies.sql
psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 -f supabase/migrations/0003_roles.sql

# 2. set the app role's password OUT OF BAND (never in a repo file, never pasted into a ticket)
psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 -c "alter role auditorai_app password '<operator-generated>';"

# 3. give the app its OWN url under a NEW name, in the deployment env:
#    TENANT_POSTGRES_URL = the pooled auditorai_app connection string.
#    The platform-injected POSTGRES_URL (owner role) stays as it is and is
#    NEVER used by the app — it must not be repointed.

# 4. migrate the KV data (dry run first, then apply)
npx tsx scripts/migrate-kv-to-postgres.ts
npx tsx scripts/migrate-kv-to-postgres.ts --apply --target-label ca-central-1-postgres --confirm-target ca-central-1-postgres

# 5. flip the switch LAST
#    TENANT_STORE=postgres
```

### ORDERING — operator ACTION-1 (the switch flips LAST; the merge is safe either way)

**The merge auto-deploys.** Every push to `main` auto-deploys to production
(`docs/deployment.md:5` — Vercel, region `iad1`).

**Why the switch exists.** Production ALREADY carries a `POSTGRES_URL` — the
platform injects it when the Supabase project is linked, and it names the
OWNER role (no tenant tables yet). A tenant path keyed off `POSTGRES_URL`
would therefore take the Postgres branch on the live MVP the moment the merge
lands, the pool factory would refuse the owner role, and **every request
would fail**. So the Postgres tenant path is **explicit**: `TENANT_STORE=postgres`
AND `TENANT_POSTGRES_URL` (the `auditorai_app` role). Until the operator flips
`TENANT_STORE`, the app keeps today's Upstash/KV path, whatever `POSTGRES_URL`
says.

The operator's steps, in order — **do not reorder**:

1. **Create the app role.** Apply `0001` → `0002` → `0003` in order with
   `psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 -f <file>` (0003 creates
   `auditorai_app`; do not reorder, do not skip). Then set its password OUT OF
   BAND: `alter role auditorai_app password '<operator-generated>';` — the
   password is generated by the operator, never in the repo, never in a ticket.
2. **Give the app its own URL under a new name.** Add `TENANT_POSTGRES_URL` =
   the pooled `auditorai_app` connection string to the deployment env. The
   platform-injected `POSTGRES_URL` (owner role) is NEVER used by the app and
   must not be repointed.
3. **Migrate the KV data.** Dry run first, then apply:
   `npx tsx scripts/migrate-kv-to-postgres.ts` then
   `npx tsx scripts/migrate-kv-to-postgres.ts --apply --target-label ca-central-1-postgres --confirm-target ca-central-1-postgres`
   (the script targets `TENANT_POSTGRES_URL`; the KV source stays the rollback
   path).
4. **Flip the switch LAST.** Set `TENANT_STORE=postgres`. Until this value is
   set the app keeps today's Upstash path whatever `POSTGRES_URL` says;
   flipping it before step 3 means Postgres serves NO workspace until the
   credential rows exist — each workspace keeps being served by the legacy
   store until its credential row is backfilled.
5. **Verify.** A migrated workspace answers with
   `database_status.database_state === "postgres"`; an unmigrated one still
   answers from Upstash with the plain "database not configured" notice.

## The role invariant (and the one escape hatch)

The tenant connection MUST be the `auditorai_app` role: NOSUPERUSER,
NOBYPASSRLS, and the owner of nothing. `FORCE ROW LEVEL SECURITY` binds a
plain table owner (a superuser or `BYPASSRLS` role still bypasses it). The
operator's owner credentials in Supabase are privileged, so that connection
— and any service-role key — reads every tenant's rows: keep it out of the
request path. The isolation guarantee comes from the app role, not from the
policies alone. The application sets it transaction-locally on every
transaction (`set local role auditorai_app`).

**`DB_ALLOW_OWNER=1` — out-of-band operator escape hatch.** If
`TENANT_POSTGRES_URL` still names the owner role, the pool factory refuses to
build. The operator can bypass that refusal by exporting `DB_ALLOW_OWNER=1` in
the process environment (it is deliberately not a project env name and is not
listed in `.env.example`).

> **Using `DB_ALLOW_OWNER=1` VOIDS the isolation guarantee.** It runs the
> tenant path as a role that owns the tables and therefore bypasses RLS, so
> every policy in `0002` becomes a no-op and one workspace can read another's
> rows. It exists so the operator can unblock a deployment during an incident;
> it is not a supported configuration. Fix `TENANT_POSTGRES_URL` instead.

`TENANT_POSTGRES_URL` must point at the `auditorai_app` role — with the
password set in step 1 — for the isolation guarantee to hold.

## How the identity reaches the database

The tenant identity travels as two transaction-local GUCs, set with
`set_config(..., true)` inside the same transaction as the query (the Supabase
pooler is transaction-pooled, so a session-level `SET` would be discarded):

| GUC | Set by | Read by |
|---|---|---|
| `request.jwt.claims` | `{"sub": "<subject>", "workspace_id": "<uuid>"}` | `public.app_claim_subject()`, `public.app_claim_workspace_id()` |
| `request.credential_hash` | the presented credential's 16-hex `workspaceHash(key)` | `public.app_claim_credential_hash()` |

The `workspace_credentials` policies are keyed on the **second** GUC and
reference **no table**, so the credential row is visible to its own lookup
without any policy recursion.

## Reverse path

- **Cutover rollback:** unset `TENANT_STORE` (the whole tenant path goes back
  to the legacy KV store) and/or delete the workspace's `workspace_credentials`
  row (an owner action via `POSTGRES_URL_NON_POOLING`, not an app-role one) —
  the credential no longer resolves and the legacy KV store serves that
  workspace again. Nothing else is touched.
- **Schema rollback:** `drop table` in reverse order
  (`artifact_summaries`, `artifacts`, `attachments`, `audit_issues`, `audits`,
  `projects`, `workspace_credentials`, `workspace_members`, `workspaces`).
  For #55 prepend `audit_trail_entries` to the front of that list.
  This destroys only the Postgres copy; the KV source is never destroyed by any
  code path.

## Operator procedure — ticket #54 (seats, invites, actor columns)

Apply `0004` after `0001 → 0002 → 0003`, out of band, never by an agent.

```bash
# 0. the operator's shell has the direct connection string; it is never in the repo
export POSTGRES_URL_NON_POOLING='<operator-supplied direct connection string>'

# 1. apply the #54 migration (never by an agent)
psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 -f supabase/migrations/0004_seats_invites.sql

# 2. the seat allowance of a workspace (the entitlement). The app may only
#    READ it (OD19); this statement is the only way it is written.
psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 \
  -c "update public.workspaces set seat_count = 25 where id = '<workspace-uuid>';"

# The default a NEW workspace gets is 1 (column default). There is no env var
# (SEAT_COUNT_DEFAULT is dropped); the operator provisions the number via the
# statement above.

# 3. the FIRST member of the workspace is its owner — provisioned OUT OF BAND
#    (the app never creates an owner or a workspace, OD18):
psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 \
  -c "insert into public.workspace_members (workspace_id, subject_id, role, email, status, accepted_at)
      values ('<workspace-uuid>','<supabase-user-uuid>','owner','owner@firm.com','active', now());"

# 3b. the owner's FIRST credential (the app route cannot issue one): the key is
#     operator-generated and the row is keyed by the SAME 16-hex workspaceHash
#     the app computes (sha256(key) truncated to 16 hex chars):
psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 \
  -c "insert into public.workspace_credentials (credential_hash, workspace_id, subject_id)
      values (left(encode(sha256('<operator-generated-key>'::bytea),'hex'),16),
              '<workspace-uuid>','<supabase-user-uuid>');"

# 4. flip the switch LAST (unchanged from #53):
#    TENANT_STORE=postgres
```

`GET /api/auth/me` surfaces the signed-in user's uuid so the operator can paste it into step 3.

### Sign-in token verification — HS256 only (important)

`src/lib/auth/supabase.ts:verifyAccessToken` verifies **HS256 with
`SUPABASE_JWT_SECRET` only**. Newer Supabase projects sign access tokens with
**asymmetric keys** (ES256/RS256, published via JWKS) and do not expose a
legacy JWT secret. On such a project the sign-in session will not verify:
either use the project's **legacy JWT secret** for this deployment, or a
follow-up must add JWKS/asymmetric verification to the same function. Nothing
else in the app depends on the signing algorithm.

Re-runnability: every statement in `0004` is idempotent (`add column if not exists`,
`create index if not exists`, `drop policy if exists` + `create policy`,
`create or replace function`, a guarded `add constraint`). A partial apply is
repaired by running the file again. `revoke`/`grant` are idempotent by
construction. No statement drops or renames anything.

## Operator procedure — ticket #55 (audit trail)

Apply `0005` after `0001 → 0002 → 0003 → 0004`, out of band, never by an agent:

```bash
export POSTGRES_URL_NON_POOLING='<operator-supplied direct connection string>'
psql "$POSTGRES_URL_NON_POOLING" -v ON_ERROR_STOP=1 -f supabase/migrations/0005_audit_trail.sql
```

Then set `AUDIT_TRAIL_SIGNING_KEY` (32+ random bytes, server-only, e.g.
`openssl rand -hex 32`). The application records trail entries without the key,
but the signed export route returns 503 until it is set. Keep retired keys to
verify old exports.

Reverse-drop order now starts with `audit_trail_entries`.

Known cutover limit: the KV → Postgres migration does NOT copy
`ws:<hash>:trail:*` keys. Export the signed JSON before cutover; the Postgres
chain starts at the cutover. Legacy cross-instance ordering is best effort;
Postgres is transactional. A store-write attacker can rewrite a suffix, so
signed exports are the notarisation.
